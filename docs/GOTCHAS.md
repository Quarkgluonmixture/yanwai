## 元规律：这个项目反复出现的失败机制

**「一个值缺席」和「一个值等于零」在显示层长得一模一样。**
坑 1、3、4 是同一个机制的三种形态：服务端没发分布 → 四条 0%；消息没有文字 → 什么都不显示；
消息不是新的 → 什么都不显示。每一次看上去都像「它坏了」或「它判得很有信心」，
而真相是「这里没有数据」。

⇒ 写显示层时先问：**空和零我分得开吗？分不开的话，用户会读成哪一个？**

## 1. Jev 的 score 分布是按索引字符串 key 的对象，不是文档写的数组

**症状**：摘要正常显示 `2.1 / 3`，但四条档位的百分比全是 0%。不报错。

**机制**：`https://docs.typesafe.ai/primitives` 的散文把 score 的 `probabilities` 写成数组
`[0.08, 0.25, 0.67]`；服务端实际发的是 `{"0":0.0,"1":0.02,"2":0.74,"3":0.24}`。
只认数组的解析器拿到空列表，而空列表在柱状图里画出来就是「全部 0%」——
**一个缺席的值伪装成了一个有信心的判断**。

⇒ 两种形状都接；并且**让「没有分布」和「分布全是 0」在类型上可区分**
（空列表 vs 全零列表），显示层据此走不同分支。
⇒ 更一般地：**TypeSafe 的散文文档和服务端实际返回不一致时，以实测为准**。接新题型前先 curl 一次看原始 JSON。

闸: tests/Yanwai.TypeSafe.Tests/SystemOneClientTests.cs — 覆盖对象形状解析与「缺席不等于全零」；覆盖不到显示层怎么画空分布

## 2. WPF：元素上的本地属性值压过 Style 里的 DataTrigger

**症状**：进度条高亮色永远不生效，全是灰的。XAML 看着完全正确。

**机制**：`<Rectangle Fill="{StaticResource BarFill}">` 是**本地值**，
在 WPF 的依赖属性优先级里高于 Style 的 Setter 和 Trigger。触发器确实被求值了，
只是它设的值排在本地值后面，永远赢不了。

⇒ 要被触发器改的属性，**默认值只能写在 Style 的 Setter 里**，不能写在元素上。
⇒ 这类问题 **grep 答不了**（声明存在 ≠ 它在级联里赢），只能渲染出来看。

闸: 无 — 样式优先级是运行时行为，静态检查判不了；只能靠截图核对

## 3. `OcrTextStatus.NoText` ≠ OCR 失败

**症状**：对方发了个表情，面板一动不动，看着像程序死了。

**机制**：表情 / 图片 / 语音消息的气泡里本来就没有文字，OCR 返回 `NoText` 是**正确**结果。
但第一版把它和「有字但没认出来」同等对待：不发事件、不改界面，只在状态栏留一行。
上一条消息的判定卡片还留在屏幕上——**旧判断被挂到了新消息头上**，比不显示更糟。

⇒ **「本来没有文字」和「文字没读出来」是两个事实，必须分开处理。**
前者以 `[表情或图片]` 进入上下文保持对话流完整、不计入 OCR 失败计数；
后者排除出上下文并告警。两者都要清空旧卡片并说明原因。

闸: tests/Yanwai.TypeSafe.Tests/TextlessTurnTests.cs

## 4. 实时模式开启前就在屏幕上的消息，永远不会触发判定

**症状**：打开实时模式，对方那条消息明明在屏幕上，什么都没发生。

**机制**：observer 把首次观察到的可见消息建成**基线**（`Bootstrap`），只有基线之后新出现的
才是 `LiveNew`。这是**防止把历史消息当新消息重放**的设计，不是 bug。

⇒ 验证实时链路时，必须让消息在**开启之后**到达。
⇒ 排查「没反应」时，先分清是 Bootstrap、OCR 不可信、还是真的没收到——
面板「正在判断的消息」还是 `—` 就说明一条都没走到判定。

闸: 无 — 需要真实新消息到达才能区分，机器造不出来

## 5. 只设 Topmost 不看前台 = 浮层糊在别的应用上

**症状**：切到浏览器 / 终端，HUD 还稳稳浮在最上面。

**机制**：`Topmost=True` 的语义就是「压住所有非置顶窗口」，它不关心你在看哪个应用。

⇒ 跟随逻辑里必须要求 `snapshot.IsForeground`，微信不在前台就隐藏。
⛔ 别只判 `IsVisible && !IsMinimized`——那两条在微信被别的窗口盖住时都是 true。

闸: 无 — 前台状态是运行时的；单测覆盖了 Place 的几何，覆盖不到这条

## 6. 面板进程开着的时候构建会失败（MSB3027 / MSB3021）

**症状**：`The process cannot access the file ... because it is being used by another process`。

**机制**：`Yanwai.Panel.exe` 还跑着就锁住了它 `bin` 下的依赖 DLL。

⇒ 改完代码重新构建前先 `Get-Process -Name Yanwai.Panel | Stop-Process -Force`。
⇒ 同理，`dotnet` 的常驻编译服务器会攥着**旧路径**——移动或改名 SDK / 仓库目录前
先 `dotnet build-server shutdown`，否则移动会半途失败留下混合状态。

闸: 无 — 可以做成构建前的 pre-step，还没做（见 TODO）

## 7. `global.json` 钉死 8.0.425，系统 SDK 是 9.0.101

**症状**：`A compatible .NET SDK was not found. Requested SDK version: 8.0.425`。

**机制**：`global.json` 的 `rollForward: latestPatch` 只接受 8.0.4xx。
仓库脚本用的是私有 SDK：`%LOCALAPPDATA%\Yanwai\dotnet\dotnet.exe`，
**不在 PATH 上**，`scripts\*.ps1` 存在就优先用它、不存在就退回系统 dotnet。

⇒ 直接敲 `dotnet build` 会失败；走 `scripts\build.ps1`，或显式用私有 SDK 的全路径。
⇒ 改项目名 / 搬目录时这个路径字符串跟着改，**目录也要一起搬**——
否则脚本会静默退回系统 SDK，然后你收到的是一条看不出根因的 global.json 报错。

闸: 无 — scripts/*.ps1 的 fallback 逻辑本身就是闸的一半，但它不会告诉你为什么退回了

## 8. `EnumWindows` 回调里不能让异常逃出去，但可以大声吞

**症状**：微信永远找不到，界面只说「找不到窗口」，没有任何线索。

**机制**：`EnumerateCandidates` 在原生 `EnumWindows` 回调里 `catch (Exception) {}`，
注释说是为了「窗口枚举期间消失」——可那种情况 `TryCreateCandidate` 内部已经接住了
（`ArgumentException` / `InvalidOperationException` → 返回 null）。
所以外层能吞到的按构造**只剩真 bug**，而它一声不吭。

**但也不能改成往上抛**：异常逃出 P/Invoke 回调会直接把进程撕掉。

⇒ 这类「必须吞」的边界，走**吞了但记下来**：计数 + 记住第一条，
由调用方在「没找到窗口」时一并报出来。
⇒ 推广：**兜底路径不记录 = 每一次调用都悄悄变坏，而日志和界面看上去正常**。

闸: 无 — 需要注入一个会抛的候选工厂才能测，为此重构不划算

## 9. `--depth 1` 浅克隆会把历史截断，push 出去就永久少了

**症状**：`git log` 只有 1 个 commit，实际上游有 22 个。

**机制**：浅克隆只取一层。在它上面接着提交、再推到新仓库，推上去的就是被截断的历史。

⇒ 要长期维护的仓库**不要浅克隆**；已经浅克隆了又想转正，
**fork + 完整 clone + 把本地分支 fetch 过去**，比 push 一个浅仓库干净得多
（这样祖先链还接在原始 first commit 上，出处也留着）。

闸: 无 — clone 参数是一次性动作

## 10. OCR 的置信度会对缺字给满分；拿来核对的引擎可能比主引擎还差

**症状**：「诶哟我去」读成「哟我去」，置信度 1.00。或者：Paddle 读对了，却因为核对引擎读成别的而被判不可信，
屏幕上大半消息没有卡片。

**机制**：PP-OCRv6 的字典里**没有「诶」**，模型不可能输出它，于是直接跳过，分数照样满。
反过来，Windows OCR 在深底白字上会**整条返回空**，把「怎么说」读成「怎久说」——
严格要求两个引擎一致，等于让更差的那个一票否决。

⇒ 信任靠两个引擎**大体一致**（`CrossCheckedOcrEngine`：差 ≤20% 的字，缺的字若主引擎根本输出不了就采纳核对方），
不靠任何一方的分数。核对方要喂**同样的逐行紧裁剪、转成白底黑字**（`LineWiseOcrEngine`）。
⇒ 仍核对不上的**照样判定，但标「OCR 未核实」并把判的原文显示出来**，不悄悄丢，也不悄悄当真。
⇒ 换模型时先查字典覆盖常用语气词：`诶` 这类缺字不会报错。

闸: tests/Yanwai.Ocr.Tests/CrossCheckedOcrEngineTests.cs — 覆盖信任规则（逐行裁剪另见同目录 TextLineSplitterTests.cs）；覆盖不到真屏幕上两个引擎的一致率，那半只能用 `--ocr-compare-live` 人工看

## 本项目特有的硬规则

- ⛔ **不注入微信、不 hook、不读本地加密数据库、不自动回复**。见 `AGENTS.md`。
- ⛔ **聊天原文不落盘**。debug 截图是显式动作且已 gitignore；实时模式只在内存里跑。
- ⛔ **`TYPESAFE_API_KEY` 不进仓库、不进日志、不进截图**。只从环境变量读。
- ⛔ **问题集不问人品**：只问可观察的对话行为，不问对方是否撒谎 / 是否操纵 / 性格标签。
  见 `AGENTS.md` 的 "Do not over-interpret conversation semantics"。

## 准入判据

两个闸门必须**同时**成立才写进这里：

1. **未来还会遇到**（不是只发生过一次的偶发），且
2. **当时不会报错**（静默——编译器、测试、界面都不会告诉你）。

会报错的 → 修掉就行。被测试抓得到的 → 那条测试就是闸，写墓碑不写条目。
只发生过一次且有明确根因的 → `LOG.md` 打 `#incident`。
纯粹的未完成工作 → `TODO.md`。
